# Windows UI Implementation Brief

Status: approved visual direction; implementation intentionally paused until Windows functionality is stable.

## Scope and mode

- Surface: the complete Windows desktop client.
- Mode: operate.
- Primary user task: inspect Codex connectivity, manage tweak packages, inspect logs, and control application updates without editing files manually.
- Platform rule: use the current Windows 11 / WinUI 3 Fluent design language without a separate branded visual skin.
- Cross-platform rule: keep the same four destinations, section order, information grouping, and primary-action placement as the macOS SwiftUI client. Use platform-native controls and interaction patterns on each OS.

- Primary composition: [Windows Store-style package catalog](../.impeccable/mocks/windows-store-catalog.png)
- Spacious overview reference: [Windows Settings-style overview](../.impeccable/mocks/windows-settings-standard.png)
- Grouped-control reference: [PowerToys-style package group](../.impeccable/mocks/windows-powertoys-groups.png)

The primary composition controls shell density and package scanning. It is not a literal screenshot specification. Do not copy its generated checkbox column, duplicate package toggle, persistent details panel, synthetic icons, or any value that is not present in the Go snapshot. The production package list follows the macOS row structure and expands only real dependency or error details.

## Direction contract for the future XAML root

THESIS: one business state expressed through the native Windows 11 workspace; refuse both a web dashboard and a custom developer-tool skin.

OWN-WORLD: system Mica, system theme brushes, Segoe UI Variable, Fluent icons, native control templates, and restrained two-layer elevation.

STORY: users see Codex state first, find the same four destinations as macOS, and act next to the state or package the action changes.

FIRST VIEWPORT: a left NavigationView and transparent content page; page title and summary lead, contextual actions follow, and current state occupies the main content layer.

FORM: Windows 11 Fluent canon, chosen explicitly by the user; composition delegated to the implementation and anchored by the approved package-list mock.

FINISH: unreviewed and undocumented is unfinished; this build ends with the finish review, the verdict, and DESIGN.md.

## XAML structure

```text
windows/CodexTweaks.Windows/
├── App.xaml
├── MainWindow.xaml
├── MainWindow.xaml.cs
├── Pages/
│   ├── OverviewPage.xaml
│   ├── PackagesPage.xaml
│   ├── LogsPage.xaml
│   └── UpdatesPage.xaml
├── Styles/
│   ├── Foundation.xaml
│   ├── Layout.xaml
│   └── Components.xaml
└── Generated/
    └── PresentationResources.xaml
```

- `MainWindow.xaml`: `MicaBackdrop`, custom title-bar integration where safe, left `NavigationView`, `Frame`, and one shell-level `InfoBar`.
- `Pages/*.xaml`: native layout only. Pages may bind state, forward actions, invoke pickers, open paths, copy text, and participate in Windows navigation.
- `Generated/PresentationResources.xaml`: generated by the Go Presentation Contract generator for cross-platform dimensions, semantic tones, and durations. It is never hand-edited.
- `Foundation.xaml`: aliases current Windows theme resources; defines no fixed light-only palette. It covers Light, Dark, and HighContrast.
- `Layout.xaml`: page width, page header, section spacing, settings rows, compact desktop density, and responsive breakpoints.
- `Components.xaml`: reusable visual styles for status surfaces, package rows, empty states, path rows, and command groups. It must not encode business availability or status decisions.

## Presentation boundary

Go and the generated contract remain authoritative for:

- all DTOs and state;
- every visible string;
- available actions;
- status title, detail, and semantic tone;
- package summaries and package-specific status;
- shared dimensions and motion durations.

C# and XAML own only:

- navigation and focus;
- binding and view-state such as selection, search text, and expanded rows;
- Windows pickers, clipboard, path launching, title bar, and Velopack interaction;
- mapping semantic tones to Windows theme resources.

## Page parity

| Shared destination | macOS | Windows |
| --- | --- | --- |
| Overview | `NavigationSplitView` detail, status card, control/AI/resources groups | `NavigationView` page, status `InfoBar`/surface, the same three groups |
| Packages | header and environment state, install/update actions, search/filter, package rows | the same sequence using `CommandBar`, `InfoBar`, `AutoSuggestBox`, and `ListView` rows |
| Logs | action row plus monospaced selectable log | the same sequence using command buttons and a read-only monospaced text surface |
| Updates | app identity group plus update preferences/status group | the same two groups, with Velopack apply action on Windows |

## Native Windows rules

- Use `NavigationView` for the four top-level destinations and let it adapt at narrower widths.
- Use `MicaBackdrop` as the base layer and keep page roots transparent; content surfaces use Windows layer/card theme brushes.
- Follow the system theme and accent color. Support Light, Dark, and HighContrast without hard-coded backgrounds.
- Use Segoe UI Variable and built-in XAML type styles. Use Segoe Fluent Icons through native icon elements; do not use Unicode glyphs or emoji.
- Scope the official compact-density dictionary to package commands, filters, and dense form controls; keep touch-sized navigation and primary controls at default density.
- Use `InfoBar` for non-modal status/error feedback and `ContentDialog` only for decisions that require interruption.
- Preserve keyboard navigation, visible focus, automation names, text scaling, and reduced-motion behavior.
- Never reintroduce WinUI `NumberBox` for package priority on Windows ARM64; use a validated plain `TextBox`, with the Go backend remaining the final validator.

## Implementation order after functional stabilization

1. Generate `PresentationResources.xaml` from Go and verify deterministic generation.
2. Add XAML shell and navigate empty pages without changing backend behavior.
3. Port Overview, Packages, Logs, and Updates one at a time from the existing thin-client calls.
4. Remove the programmatic visual tree only after all four pages pass on Windows ARM64.
5. Run Light, Dark, HighContrast, keyboard, text-scale, narrow-window, install, update, and uninstall QA.
6. Write `DESIGN.md` from the built and verified result, then run the final visual review.
